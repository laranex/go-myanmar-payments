# Changelog

All notable changes to `go-myanmar-payments` will be documented in this file.

## v4.0.0 - Unreleased

Initial release. The version number matches the other Laranex packages (`php-myanmar-payments`, `laravel-myanmar-payments`), so the module path carries the major version: import `github.com/laranex/go-myanmar-payments/v4` and its sub-packages (`.../v4/kbzpay`, `.../v4/wavepay`, `.../v4/ayapay`, `.../v4/yomammqr`, `.../v4/cybersource`).

### Added
- `payments.New(payments.Config{...}, payments.Options{...})` and `payments.FromEnv(getenv, options)` build each gateway (`KBZPay()`, `WavePay()`, `AYAPay()`, `YomaMMQR()`, `CyberSource()`) once, on first use, and are safe for concurrent use.
- Gateways: KBZ Pay (`PWA`, `QR`, `App`, `Status`, `Signer`), Wave Pay (`Initiate`), AYA Payment Gateway (`Services`, `Initiate`, `Status`, `VerifyRedirect`), Yoma MMQR (`Initiate`, `RenewQR`, `Status`, `ForgetToken`) and CyberSource Secure Acceptance (`Initiate`); every gateway validates its `PaymentData` and verifies callbacks with `HandleCallback`.
- Exact `Amount` type (`Kyat`, `ParseAmount`, `MustParseAmount`, `Equals`, `WholePart`) kept as decimal text, so amounts never pass through a float; JSON marshals as a string and unmarshals from a string or a number.
- Configuration: a `Config` struct per gateway plus `ConfigFromEnv(getenv)`, which reads the same variables as the PHP packages. Every setting of a gateway you use is required and has no default, URLs included (the `Production*` constants only name production's; the `Resolved*URL()` methods return the configured URL without its trailing slash), except the HTTP timeout (`TimeoutSeconds`, `MYANMAR_PAYMENTS_HTTP_TIMEOUT`), which defaults to 30 seconds (`myanmarpayments.DefaultTimeoutSeconds`); a nil HTTP client becomes an `*http.Client` with that timeout, and a client you pass keeps its own. Required settings include KBZ Pay's `TimeToLiveMinutes` (`KBZ_PAY_TIME_TO_LIVE_IN_MINUTES`, 1 to 120), Wave Pay's `TimeToLiveSeconds` (`WAVE_PAY_TIME_TO_LIVE_IN_SECONDS`) and `MerchantName`, and Yoma MMQR's `APIVersion` and `WebhookSecret` (`YOMA_MMQR_WEBHOOK_SECRET`). A missing or blank setting returns the `ConfigurationError` naming it; time settings above 2147483647 are invalid; settings are checked as the required strings, then the time to live, then the timeout; a value out of range returns one with `Invalid` set, e.g. `The kbz_pay configuration [time_to_live_in_minutes] must be a whole number from 1 to 120.`
- Payment data: `kbzpay.PaymentData.TimeToLiveMinutes` and `wavepay.PaymentData.TimeToLiveSeconds` (`*int`) override the configured time to live, and `wavepay.PaymentData` takes an optional `MerchantName`; CyberSource payments take `Currency`, `Locale` and `TransactionType`. Wave Pay follows the Pay with Wave API spec v1.3: payments are a JSON post to `BaseURL`'s `/payment` (Content-Type and Accept `application/json`) with `amount` and `time_to_live_in_seconds` as JSON integers, `currency` `MMK` and `items` as a JSON string array, and the customer is sent to `BaseRedirectURL`'s `/authenticate` (UAT: `https://preprodpayments.wavemoney.io:8107` for both; production: `wavepay.ProductionURL`, `https://payments.wavemoney.io`). `wavepay.PaymentData` takes optional `AdditionalField3`, `AdditionalField4` and `AdditionalField5` (at most 50 characters each, sent as `additional_field_3` to `additional_field_5` only when non-empty) and enforces the spec's limits: `OrderID` and `MerchantReferenceID` at most 100 characters, `CallbackURL`, `ReturnURL` and `Description` at most 255 (bytes of UTF-8). `Initiate` validates before filling an empty `MerchantReferenceID`, so invalid data is returned untouched. Callback, return and cancel URLs are checked like PHP's `FILTER_VALIDATE_URL` with an http or https scheme, the same rule in every Laranex SDK: printable ASCII only, a host of letters, digits and inner `-` labels (or a bracketed IP) and a port from 0 to 65535. A negative amount is reported with the other field errors as `The amount field must not be negative.`; Wave Pay checks `merchantReferenceId` after `items` and reports a scalar 422 error entry (`amount: too small`); an AYA user ref holding `:` is reported once under `userRefs`. Field, amount and currency rules follow each gateway's official documentation.
- Result types: `RedirectPayment`, `FormPayment` (`HTML`, `HTMLWithNonce` for a CSP nonce), `QrPayment` and `AppPayment` for payment flows, `PaymentCallback` (with a gateway-independent `PaymentStatus`, `PaymentStatuses()` and the `Acknowledgement` each gateway expects) for verified callbacks, and `PaymentStatusResult` for status checks.
- Wave Pay callback statuses per the spec: `PAYMENT_CONFIRMED` is successful; `BILL_COLLECTION_FAILED`, `INSUFFICIENT_BALANCE` and `ACCOUNT_LOCKED` are failed; `SCHEDULER_TRANSACTION_TIMED_OUT` (and `TRANSACTION_TIMED_OUT`) is expired; `PAYMENT_REQUEST_CANCELLED` is canceled.
- Callback verification: Wave callbacks fall back to `merchantReferenceId` for the order id when `orderId` is missing, null or empty, and need a decimal amount and well-formed ids; CyberSource trusts only signed fields (`decision` and `req_reference_number` must be signed, the amount and `transaction_id` are read only when signed, and `Raw` keeps only the signed fields plus `signature`), its `signed_field_names` must sign itself with no empty, repeated or `=` names, and `decision` must be a known one; AYA checksum values may not hold `:` (except a well-formed `dateTime`), results need an order, transaction, MMK amount and two-digit status, and a `+` in the base64 `payload` that arrived as a space is mapped back before decoding; Yoma MMQR checks `X-Webhook-Secret` in constant time on every callback; `NewCallbackRequestFromHTTP` reads at most 64 KiB. A bad signature, hash or checksum fails with `… verification failed.`; a correctly signed Wave Pay, AYA or CyberSource callback with bad values fails with `Wave Pay callback is malformed.`, `AYA Pay {callback|redirect|enquiry response} payload is malformed.` or `CyberSource callback is malformed.`. Urlencoded bodies and query strings are decoded like PHP's `Form::decode` (a bad `%` escape is kept, `;` is no separator, the first value wins), only ASCII whitespace and NUL are trimmed (bodies, statuses, settings and required fields), `HeaderValue` joins a repeated header with `", "`, and the default HTTP client never follows redirects.
- Typed errors: `InvalidPaymentDataError`, `APIError`, `SignatureVerificationError` and `ConfigurationError`, all implementing the `PaymentError` interface.
- `HTTPDoer` and `TokenCache` abstractions so any HTTP client or cache can be plugged in; `MemoryTokenCache` ships with the module. Yoma MMQR's concurrent calls share one in-flight token request, bounded by the timeout; a caller whose context ends stops waiting without failing the others, and a token fetched before `ForgetToken` is never cached.
- Behavior is identical to `php-`, `node-` and `python-myanmar-payments`, checked by the shared vectors in `testdata/parity/vectors.json`: signing (a nested value in a signed field fails verification), callback decoding, AYA's base64 rules, the Yoma MMQR token cache key (`myanmar-payments.yoma-mmqr.token.<sha256(baseUrl|clientId)>`), `FormPayment.HTML` and every error message after the `myanmarpayments: ` prefix.
- Standard library only; Go 1.22 or higher.
- Agent skill in `skills/go-myanmar-payments` so coding agents (Claude Code, Codex, Cursor and others) integrate the module correctly; install it with `npx skills add laranex/go-myanmar-payments`.
